# ТЗ / Промпт: Веб-редактор форм на базе JSON Forms

> Этот документ — полное техническое задание (промпт) для разработки приложения.
> Его можно передать разработчику или AI-агенту целиком: он содержит цель, стек,
> функциональные требования, архитектуру, этапы и критерии приёмки.

---

## 1. Роль и цель

Ты — senior frontend-архитектор и разработчик. Твоя задача — спроектировать и
реализовать **веб-приложение — визуальный конструктор форм**, который:

1. Позволяет собирать формы drag-and-drop из палитры элементов.
2. Генерирует стандартные артефакты [JSON Forms](https://jsonforms.io/):
   **JSON Schema** (данные) и **UI Schema** (представление).
3. Позволяет настраивать каждый элемент (валидация, дефолты, источники данных и т.д.).
4. Позволяет **выбирать и кастомизировать UI-библиотеку рендеринга** (Material, AntD,
   Vanilla и др., а также собственные наборы на базе Radix UI и любых компонентов),
   сохранять эти наборы и использовать их в сторонних проектах.
5. Дает возможность запустить собранную форму в режиме превью и посмотреть
   итоговые данные.

Главный нефункциональный приоритет: **архитектура, рассчитанная на рост** —
новые типы элементов, новые UI-наборы, новые типы правил добавляются как
расширения, без переписывания ядра.

## 2. Технологический стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Фреймворк | **React 18+ + TypeScript** | обязательное требование заказчика |
| Сборка | **Vite** | быстрый dev-сервер, простая конфигурация |
| Движок форм | **@jsonforms/core, @jsonforms/react** | стандарт де-факто для schema-driven форм |
| Рендереры | **@jsonforms/vanilla-renderers, @jsonforms/material-renderers, @great-expectations/jsonforms-antd-renderers (комьюнити)** | предустановленные пресеты; уточнено в ходе разработки: официальных пакетов antd/fluent в npm нет |
| Drag-and-drop | **dnd-kit** (@dnd-kit/core, @dnd-kit/sortable) | поддержка вложенных контейнеров, вставка между элементами, touch/keyboard |
| Состояние | **Zustand** (store конструктора) + собственный document model | JSON Forms внутреннее состояние не должно смешиваться со состоянием конструктора |
| Валидация схемы | **AJV** (через @jsonforms/core) | стандарт JSON Forms |
| Иммутабельность/утилиты | immer, nanoid | удобные обновления дерева |
| Экспорт файла | Blob + URL.createObjectURL | без зависимостей |
| UI редактора | **Radix UI** (primitives) | headless-компоненты самого приложения: диалоги, поповеры, вкладки, тултипы, dropdown — с готовой доступностью (a11y) и клавиатурной навигацией |
| Стили редактора | Tailwind CSS поверх Radix | UI редактора полностью независим от UI-наборов, которыми рендерятся конструируемые формы |

**Важно:** JSON Forms не является обязательным как движок внутри самого конструктора
(конструктор работает со своим деревом), но он **обязателен** как целевой формат
экспорта и как движок в режиме превью.

## 3. Ключевое архитектурное решение (обязательное)

Приложение хранит **внутреннее дерево документа** (`DocumentNode`), а не сырые схемы.

```ts
type DocumentNode = ControlNode | LayoutNode;

interface ControlNode {
  id: string;              // nanoid, стабилен
  kind: 'control';
  elementType: ElementType; // 'text' | 'number' | 'select' | ...
  scope: string;            // JSON pointer, генерируется автоматически (#/properties/fieldName)
  schema: JsonSchemaFragment;   // фрагмент JSON Schema поля
  uischemaOptions: UISchemaOptions; // label, placeholder, description, format, варианты и т.д.
  dataBinding?: DataBinding;     // источник данных (см. раздел 5)
  validationRules?: ValidationRule[]; // см. раздел 6
}

interface LayoutNode {
  id: string;
  kind: 'layout';
  layoutType: 'vertical' | 'horizontal' | 'group' | 'categorization';
  label?: string;         // имя секции
  children: DocumentNode[];
  options?: Record<string, unknown>; // variant, justify, gap и пр.
}
```

Из дерева **сериализуются** оба артефакта:
- `toJsonSchema(tree): JSONSchema7`
- `toUiSchema(tree): UISchemaElement`

И работает обратная операция: `importFromSchemas(jsonSchema, uiSchema): tree` —
чтобы можно было загрузить сохранённую форму и продолжить редактирование.
Это решение критично: не редактировать напрямую два параллельных JSON-файла,
а иметь одну каноничную модель.

### Реестры (plugin-архитектура)

Всё расширяемое — через реестры, а не if/else:

```ts
// Реестр типов элементов палитры
interface ElementTypeDef {
  type: ElementType;
  displayName: string;
  icon: ReactNode;
  category: 'input' | 'choice' | 'layout' | 'advanced';
  defaultSchema: () => JsonSchemaFragment;
  defaultUiOptions: () => UISchemaOptions;
  propertyGroups: PropertyGroupDef[]; // описание полей инспектора (см. 4.4)
  tester: (schema, uischema) => boolean; // для сопоставления с рендерерами
}

// Реестр UI-наборов (renderer sets)
interface RendererSetDef {
  id: string;
  displayName: string;
  renderers: JsonFormsRendererRegistryEntry[];
  cells?: JsonFormsCellRegistryEntry[];
  fields?: JsonFormsFieldRegistryEntry[];
}
```

Новый тип элемента = одна запись в реестре. Новая UI-библиотека = один модуль,
регистрирующий RendererSet. Никакие изменения в ядре не требуются.

## 4. Функциональные требования

### 4.1. Палитра элементов (левая панель)

Полный список, сгруппированный по категориям:

**Ввод текста**
- Text (single line) — поддерживает format: email, password, tel, url, color
- Textarea (multiline)
- Number (integer / number)
- Slider (range с шагом, min, max, отображением значения)
- Date, Time, DateTime

**Выбор**
- Checkbox (boolean)
- Checkbox group / Multi-select (array с uniqueItems из enum)
- Radio group (один из списка)
- Dropdown / Select (enum)
- Autocomplete / combobox (enum + фильтрация, free text опционально)
- Toggle / Switch

**Продвинутые**
- File upload (string с format: data-url / binary)
- Array (повторяющийся блок — repeater: «добавить элемент», с вложенным содержимым)
- Object (вложенная группа полей)
- Rating (integer 1..n, опционально)
- Hidden field (передаёт значение, не отображается)

**Служебное**
- Label / текстовый блок (uischema Label — не влияет на данные)
- Разделитель (Divider)

Палитра должна поддерживать **drag в рабочую область** и поиск/фильтр по названию.
Клик по элементу палитры (без drag) добавляет его в конец формы или в выбранный контейнер.

> Расширяемость: каждый элемент описывается `ElementTypeDef` (см. раздел 3),
> включая описание полей собственных настроек. Добавление «Color picker» или
> «Signature pad» не должно требовать правок вне реестра.

### 4.2. Рабочая область (Canvas) и drag-and-drop

Требования к DnD (dnd-kit, SortableContext):

1. Элемент встаёт **точно туда, куда отпущен**: между двумя соседями — между ними.
   Визуальные **insertion indicators** — линия-курсор между элементами при перетаскивании.
2. Поддержка **вложенности**: элемент можно перетащить внутрь секции; при наведении
   на контейнер подсвечивается зона вложения; drop «между» внутри контейнера
   вставляет внутрь этого контейнера на нужную позицию.
3. Drag палитры → canvas (новый элемент) и drag внутри canvas (перестановка) —
   единый механизм.
4. **Защита от невалидных вложений**: например, нельзя вложить секцию саму в себя
   или в своего потомка (проверка при drag-over, drop блокируется с индикацией).
5. Клик по элементу на canvas — выделение (outline) + открытие инспектора свойств.
6. Выделенный элемент: кнопки/контекстное меню — **дублировать, удалить,
   переместить вверх/вниз** (дублирование важно для однотипных полей).
7. Undo/Redo всей истории операций конструктора (история снимков дерева,
   минимум 50 шагов, горячие клавиши Ctrl+Z / Ctrl+Shift+Z).
8. Пустой canvas показывает placeholder-подсказку («Перетащите элементы сюда»).

### 4.3. Секции и группировка

- **Vertical Layout** — вертикальный стек.
- **Horizontal Layout** — горизонтальный ряд (элементы в строку; для control-ов
  — сетка: настраиваемое число колонок / flex-grow для каждого элемента).
- **Group** — секция с рамкой и **заголовком** (имя секции задаётся в инспекторе,
  опционально: описание, сворачиваемость — collapsible).
- **Tabs (Categorization)** — вкладки; каждая вкладка = Vertical layout внутри.

Имя секции — необязательное поле; если не задано, Group рендерится без заголовка.
Секции перетаскиваются из той же палитры (категория «Секции») и принимают элементы.
Также кнопка «Сгруппировать выделенные» — обернуть выбранные элементы в новую секцию.

### 4.4. Инспектор свойств элемента (правая панель)

**Принцип прогрессивного раскрытия** (прямое требование заказчика: базовое — сразу,
остальное — по запросу):

- **Вкладка «Основные»** — всегда видимая, содержит только самые частые свойства типа:
  - name/label элемента, description/help-текст
  - placeholder
  - default value
  - required (toggle)
  - для choice-элементов: редактор списка вариантов (добавить/удалить/переупорядочить,
    поддержка label:value пар)
  - для чисел/слайдеров: min, max, step
- **Вкладка «Дополнительно»** — сворачиваемые группы оставшихся свойств:
  - формат и маска: format (email/tel/...), regex-паттерн (с **валидатором регулярки
    «на лету»**: поле «пример валидного значения» и подсветка совпадения)
  - minLength/maxLength, multipleOf, exclusiveMin/Max
  - readOnly / disabled / hidden (ui rule: скрыть при условии)
  - grid/flex настройки (в horizontal layout)
  - массив `uischema.options` — свободные доп. опции (ключ-значение), для опций
    конкретного рендерера
- **Вкладка «Правила»** — условная логика UI Schema (`rule`: visible/enabled + JSON Schema
  condition на другое поле), построитель условий по форме («если поле X = Y → показать»).
- **Вкладка «Данные»** — источник данных (см. 5) и маппинг поля на путь данных.

Реализация: свойства описаны декларативно в `propertyGroups` у ElementTypeDef,
инспектор рендерится из описания — так добавление свойств новому типу элемента
не требует правки инспектора. Список «добавить свойство вручную» — поиск по
всем допустимым опциям типа + свободное поле для нестандартных опций.

Также в инспекторе для layout-ов: имя секции, вариант отображения, gap, и т.п.

### 4.5. Источники данных (data binding)

На вкладке «Данные» для choice-элементов (select/radio/autocomplete/multiselect):

1. **Статический список** (по умолчанию) — enum, редактируется в инспекторе.
2. **Внешний источник (URL)** — поля:
   - URL (template-строка, может содержать `{{...}}` подстановки из контекста)
   - метод (GET), заголовки (ключ-значение), query-параметры
   - **JSONPath/pointer к массиву элементов** в ответе (например `$.data.items`)
   - маппинг: какое свойство элемента — value, какое — label
   - режим: загрузить один раз / обновлять при открытии формы / при вводе
     зависимого поля (dependency на другое поле)
3. **Из контекста** — значение берётся из другой части данных формы или из
   переменной, переданной в форму при инициализации.

Сериализация: источники выносятся в **отдельный манифест** (`dataBindings.json` /
секция в экспорте), чтобы не засорять JSON Schema нестандартными ключами.
В проекте-потребителе подгружается небольшой helper `@formkit/bindings`,
который по манифесту выполняет запросы и подставляет enum/options.
Простые статические enum продолжают жить в JSON Schema как обычно.

### 4.6. Валидация

- Вся стандартная JSON Schema валидация через AJV (required, pattern, min/max,
  minLength, enum...) — формируется из свойств инспектора автоматически.
- **Сообщения об ошибках настраиваются** per-field: поле «custom error message»
  (через ajv-errors или i18n JSON Forms — использовать @jsonforms/i18n).
- Дополнительные правила на уровне формы (кросс-полевые): простой построитель
  условий «если поле A [оператор] значение B → поле C [обязательна/невалидна]
  с сообщением M», компилируется в `if/then/else` JSON Schema.
- Валидация в конструкторе: панель «Проблемы» со списком предупреждений
  (поле без scope-конфликта, дубликаты имён, ссылка на несуществующее поле в
  правиле, невалидная регулярка).

### 4.7. UI-библиотеки (renderer sets) — ключевая фича

**Концепция: «Набор рендереров» (Renderer Set).** JSON Forms рендерит форму через
реестр `renderers`, где каждая запись — пара {tester, renderer}. Всё управление
внешним видом строится вокруг подмены/кастомизации этого реестра.

#### A. Предустановленные пресеты (переключатель в тулбаре)

Из коробки установлены и переключаются «на лету» (drop-down «UI Library»):
- **Vanilla** (@jsonforms/vanilla-renderers) — со стилями по умолчанию + выбор
  готовых тем vanilla (styles/*.css)
- **Material UI** (@jsonforms/material-renderers)
- **Ant Design** (@great-expectations/jsonforms-antd-renderers, комьюнити-пакет)

> Уточнение по итогам этапа 2: официальных пакетов `@jsonforms/antd-renderers`
> и `@jsonforms/fluent-renderers` в npm не существует; AntD покрыт комьюнити-пакетом,
> Fluent исключён из пресетов (может вернуться через собственный адаптер этапа 3).

Переключение мгновенно перерисовывает canvas и превью выбранным набором —
заказчик видит, как форма будет выглядеть в каждой библиотеке.

#### B. «Своя UI-библиотека» — Style Pack (предложенное решение)

Заказчик спросил, как лучше реализовать кастомизацию. Предлагается двухуровневая
модель:

**Уровень 1 — Theme-маппинг (без кода).**
Пользователь создаёт «Style Pack»: выбирает элемент на canvas (или тип элемента в
списке) и задаёт:

> Вход по кнопке «Создать свою тему / UI-библиотеку» — открывает **отдельный
> редактор темы** (не панель в превью). Текущая панель «Оформление формы» в окне
> запуска — временный зародыш; на этапе 3 она заменяется полноценным редактором
> кастомных тем. Требование зафиксировано по итогам ревью MVP 2026-11-20.
- CSS-классы и/или inline-стили для контейнера, label, input, error-message,
  description (все стандартные классы vanilla-рендереров доступны как цели стилизации);
- CSS-переменные темы (primary color, radius, spacing, font) — единая таблица
  переменных для всего пака;
- выбор variants (outlined / filled / filled-dark и т.п., где рендерер поддерживает).

Результат сериализуется как декларативный JSON:
```json
{
  "name": "My Radix-ish Theme",
  "basedOn": "vanilla",
  "cssVars": { "--primary": "#646cff", "--radius": "8px" },
  "controls": {
    "text":   { "wrapperClass": "my-field", "inputClass": "my-input", "style": {...} },
    "select": { "componentOverride": "radix-select" }
  }
}
```
Механика: пак оборачивает базовые vanilla-рендереры HOC'ом, который применяет
классы/стили/подменяет внутренний компонент. Превью в конструкторе показывает
форму с этим паком.

**Уровень 2 — Component Override (замена на компоненты библиотеки, напр. Radix).**
Для каждой пары (тип элемента → компонент) пользователь указывает замену из
каталога подключённых компонент-адаптеров. В приложение предустанавливаются
адаптеры для популярных headless/component-библиотек:
- **Radix UI** (select, dialog, slider, switch, checkbox, popover, tabs...) —
  базовый адаптер; остаётся полностью поддерживаемой библиотекой
- **Base UI** — headless-библиотека от команды MUI; с июля 2026 — дефолт для
  новых проектов shadcn/ui, самая быстрорастущая в headless-сегменте
- **React Aria Components** (Adobe) — эталонная доступность (a11y) и поведение
  форм; третий поддерживаемый вариант в экосистеме shadcn
- **shadcn/ui** — как пресет Tailwind-стилей для code generation (поверх
  Base UI или Radix)
- **Mantine** — «всё в комплекте» библиотека; адаптер на этапе 4
- **Headless UI** — резерв для Tailwind-стека, по запросу

Обоснование (картина на конец 2026): кастомные формы в сообществе сейчас
строят в основном на headless-примитивах — Radix / Base UI / React Aria — и
shadcn/ui поверх них; все четыре адаптера закрывают подавляющее большинство
проектов. MUI и Ant Design уже покрыты предустановленными renderer set
пресетами, отдельные адаптеры для них не обязательны. Каталог при этом —
реестр: пользователь всегда может добавить свой адаптер.

Бонус синергии: UI самого редактора уже построен на Radix, поэтому адаптер Radix
не добавляет новых зависимостей в бандл и использует те же версии примитивов,
что и приложение — меньше расхождений при code generation.
- shadcn/ui (radix + tailwind) — опционально второй адаптер
- Пользователь может **загрузить свой адаптер** (см. ниже).

Адаптер — это модуль, экспортирующий map: `controlKind → ReactComponent`,
подписанный контрактом (props JSON Forms: data, handleChange, path, errors, options).
Каталог адаптеров — реестр, расширяется без правки ядра.

**Экспорт Style Pack для использования в проекте потребителя.** Два режима:

1. **Runtime-пак** (если проект потребителя тоже использует конструктор/рантайм
   этого инструмента): скачивается `.json` пака + минимальный npm-хелпер
   `createRenderersFromPack(pack, componentAdapters)` — проект регистрирует
   полученные renderers в своём `<JsonForms />`. Ради этого весь mapping и
   должен быть декларативным JSON, а не кодом.
2. **Code generation** (для произвольного React-проекта) — **обязательны оба формата**:
   - **Single-file**: генерируется `.tsx` файл(ы) — исходники кастомных рендереров
     (обёртки над компонентами выбранной библиотеки с выбранными пропсами/классами)
     + файл реестра + инструкция подключения. «Вставил — и работает».
   - **npm-пакет-шаблон**: скачивается архив-скелет готового пакета
     (`package.json`, `tsconfig.json`, `src/renderers/*.tsx`, реестр, README
     с инструкцией сборки и публикации) — для команд, которые ведут свою тему
     как внутренний npm-пакет и версионируют её.

   В обоих форматах цель одна: «в проекте, где используется radix (или другая
   выбранная библиотека), всё сразу выглядит так, как ожидалось».

#### C. Импорт и правка существующих паков

- Кнопка «Импортировать Style Pack» (.json) — пак появляется в списке доступных
  наборов, **открывается в редакторе паков** (та же вкладка кастомизации) для правки.
- Импорт кода-рендереров (сгенерированного ранее .tsx) — по желанию (этап 3):
  парсинг/анализ — можно ограничить «повторной загрузкой .json пака», чтобы не
  строить парсер TS-кода. Это осознанное упрощение — указать его в документации.

**Редактор паков** (отдельная вкладка/модальное окно):
- слева — список типов элементов формы; справа — живое превью образца элемента,
  стилизуемого на лету; снизу — редактор CSS-переменных и маппинга компонентов.
- «Сохранить пак», «Экспортировать .json», «Экспортировать код (.tsx/.zip)».

### 4.8. Экспорт / импорт формы

- Кнопки скачивания: **JSON Schema (.json)**, **UI Schema (.json)**,
  **манифест data bindings (.json)**, **Style Pack (.json)**, **полный проект**
  (один .json со всем — для повторной загрузки в конструктор).
- Кнопка «Копировать в буфер» для каждой схемы.
- Валидация перед экспортом: форма проходит проверку целостности; ошибки
  показываются в панели «Проблемы», экспорт блокируется при критических.
- Импорт: полный проект или пара schema+uischema → построение дерева (раздел 3).
- Локальная автосохранка (debounce) и список последних проектов — через
  интерфейс `StorageAdapter { list, load, save, delete }` с реализацией
  LocalStorageAdapter. **Задел под backend:** в будущем подключается
  BackendAdapter (REST API + авторизация) без изменения ни одной фичи —
  все обращения к хранилищу только через этот интерфейс. Формат файла проекта
  версионируется (`schemaVersion`) для будущих миграций при синхронизации.

### 4.9. Режим превью / тест-запуска (Playground)

Кнопка «Запустить форму» (переключает canvas в preview-режим или открывает
модальный полноэкранный режим):

1. Форма рендерится **реальным JSON Forms** с текущим renderer set и style pack.
2. Валидация через AJV (включая сгенерированные if/then правила и кастомные
   сообщения) — живые ошибки при blur/submit.
3. Ввод данных пользователем; рядом панель:
   - **Data** — текущее состояние данных формы (live JSON, с подсветкой изменений);
   - **Validation** — список активных ошибок;
   - кнопка **Submit** — показывает финальный payload, как его получит backend;
   - опция «эмуляция data binding» — для URL-источников можно подставить
     mock-ответ (редактируемый JSON), чтобы проверить select-ы без реального API.
4. Кнопка «Сбросить данные» — вернуть к дефолтным значениям из схемы.

## 5. Структура проекта (масштабируемость)

Feature-based (слои: app → features → shared), по принципу «новая фича — новая папка»:

```
src/
  app/                    # роутинг, layout, провайдеры, глобальный стиль
  features/
    document-model/       # дерево DocumentNode, операции (insert/move/remove),
                          # сериализация toJsonSchema/toUiSchema, импорт, undo/redo
    palette/              # реестр ElementTypeDef + UI палитры
    canvas/               # dnd-области, insertion indicators, рендер дерева
    inspector/            # PropertyGrid, рендер по propertyGroups, вкладки
    validation/           # правила, ajv-конфигурация, панель «Проблемы»
    databinding/          # источники данных, манифест, мок-режим
    renderer-sets/        # реестр RendererSetDef, пресеты MUI/AntD/Vanilla/Fluent
    style-packs/          # редактор паков, HOC-обёртки, генератор кода
    preview/              # playground: JsonForms+ajv+data-панель
    export/               # скачивание файлов, копирование, полный проект
    project/              # StorageAdapter (LocalStorageAdapter → в будущем BackendAdapter
                          # с авторизацией), автосейв, список проектов, schemaVersion
  shared/
    ui/                   # примитивы UI редактора (Button, Tabs, Dialog, Popover, Tooltip...)
                          # строятся на Radix UI primitives + Tailwind (стили редактора)
    lib/                  # утилиты, nanoid, immer-хелперы
  registry.ts             # центральная регистрация реестров (точка расширения)
```

Правила:
- Зависимости направлены строго вниз: features → shared; features между собой —
  только через реестры/события (не импортировать canvas из inspector и т.п.).
- Всё расширяемое — реестры (`ElementTypeDef`, `RendererSetDef`, `AdapterCatalog`,
  `ValidationRuleDef`) + центральный `registry.ts`.
- Строгий TypeScript, `strict: true`; ESLint + Prettier.
- Юнит-тесты на document-model (сериализация/импорт/undo) — Vitest.
- **Формат приложения:** standalone SPA. Ядро (document-model, реестры) держится
  независимо от UI-слоя, чтобы при необходимости вынести его в отдельный
  пакет/SDK, но monorepo и пакетную структуру на старте не заводим.

## 6. Нефункциональные требования

- Производительность: форма на 100+ элементов — drag и редактирование без
  ощутимых лагов (мемоизация узлов, виртуализация палитры при необходимости).
- Приложение полностью клиентское (без обязательного backend); все данные —
  в браузере. CORS-запросы data binding выполняет проект-потребитель,
  в конструкторе — только mock.
- Поддержка светлой/тёмной темы самого редактора — необязательна, отложить.
- Локализация интерфейса редактора: **два языка — русский и английский**,
  переключатель языка в тулбаре. i18n-каркас закладывается с первого дня:
  никаких строк интерфейса в коде, всё через словари ru/en.
- Мультиязычность **самих конструируемых форм** (лейблы и сообщения об ошибках
  на нескольких языках) — отложена отдельным этапом: сейчас все тексты формы —
  обычные строки; при необходимости переход на словари переводов (JSON Forms
  i18n) делается миграцией модели документа без смены формата экспорта.
- Браузеры: последние Chrome/Firefox/Edge.

## 7. Этапы разработки

Разработка ведётся **поэтапно**: после каждого этапа — проверка заказчиком
и корректировка до начала следующего. Первая поставка — этап 1 (MVP).

### MVP (ядро)
1. Каркас: Vite + React + TS, layout из 3 панелей + тулбар; i18n-каркас со
   словарями RU/EN и переключателем языка.
2. document-model: дерево, CRUD-операции, undo/redo, сериализация в схемы, импорт.
3. Палитра (базовые типы: text, textarea, number, checkbox, select, radio,
   slider, date) + canvas с dnd-kit (вставка между элементами, вложенность в секции).
4. Секции: Vertical, Horizontal, Group (с именем), Tabs.
5. Инспектор: вкладка «Основные» для всех базовых типов; «Дополнительно» —
   pattern, min/max, placeholder, дефолт.
6. Экспорт JSON Schema + UI Schema (download + copy); автосейв и список
   проектов через интерфейс StorageAdapter (LocalStorageAdapter).
7. Preview на vanilla-рендерерах с валидацией и панелью Data.

### Этап 2 — разнообразие и контроль
8. Остальные типы элементов (array/repeater, object, autocomplete, multiselect,
   toggle, file, rating, label, divider).
9. Правила (ui rule visible/enabled, кросс-полевая валидация if/then), панель
   «Проблемы».
10. Data binding: статический/URL/контекст + манифест + mock в превью.
11. Renderer sets: переключатель MUI / AntD / Vanilla / Fluent.

### Этап 3 — кастомизация внешнего вида
12. Style Pack: theme-маппинг (классы, стили, CSS-переменные) + живое превью.
13. Component Override: адаптеры Radix UI, Base UI, React Aria Components;
    редактор маппинга компонент↔тип.
14. Экспорт паков: runtime .json + code generation в обоих форматах
    (single-file .tsx / npm-пакет-шаблон); импорт паков; адаптеры Mantine
    и Headless UI.

### Этап 4 — полировка
15. Горячие клавиши, дублирование элементов, группировка выделенных.
16. Полный экспорт/импорт проекта, список проектов.
17. Тесты document-model, документация README (как подключить пак в свой проект).

## 8. Критерии приёмки (проверочные сценарии)

1. Перетащить text-field **между** двумя существующими полями — он встаёт ровно
   между ними; после экспорта в UI Schema порядок соответствует.
2. Создать Group с именем «Контакты», вложить внутрь Horizontal layout с двумя
   полями; экспортированные схемы корректно рендерятся в отдельном проекте с
   `@jsonforms/material-renderers` — вёрстка и заголовок совпадают.
3. Задать полю email: pattern, required, custom message, placeholder, default —
   в превью все ошибки отображаются с кастомным текстом, дефолт подставлен.
4. Создать select со статическими вариантами и второй — с URL-источником
   (mock) — оба работают в превью; экспортированный манифест содержит
   корректное описание запроса и маппинга value/label.
5. Переключить UI Library с Vanilla на Material — canvas мгновенно
   перерисовался, данные формы сохранены.
6. Создать Style Pack: переопределить select на Radix Select, задать CSS-переменную
   primary, сохранить; экспортировать .json и .tsx; в стороннем проекте
   зарегистрировать рендереры по инструкции — форма выглядит как в превью.
7. Загрузить ранее сохранённый Style Pack и полный проект — редактирование
   продолжает с того же состояния; undo работает.
8. Сценарий «запустить форму»: заполнить, получить ошибки валидации, исправить,
   submit — панель Data показывает ожидаемый payload.

## 9. Зафиксированные решения

1. **Языки интерфейса редактора** — русский и английский; i18n-словари и
   переключатель языка закладываются с первого дня (раздел 6, этап 1).
2. **Хранение проектов** — localStorage через интерфейс `StorageAdapter`;
   в будущем подключается backend с авторизацией без переработки фич —
   формат проекта версионируется заранее (раздел 4.8).
3. **Каталог адаптеров component override** — ядро этапа 3: Radix UI,
   Base UI, React Aria Components; shadcn/ui как пресет code generation;
   Mantine и Headless UI — этап 4 (раздел 4.7).
4. **Code generation** — оба формата: single-file `.tsx` и npm-пакет-шаблон
   (раздел 4.7).
5. **Режим разработки** — поэтапная поставка: этап 1 (MVP) → проверка
   заказчиком → следующие этапы (раздел 7).
6. **Формат приложения** — standalone SPA; встраиваемость (SDK/пакет) на старте
   не заводится, но ядро держится отделимым от UI (раздел 5).
7. **Мультиязычность конструируемых форм** — отложена отдельным этапом;
   тексты форм сейчас — обычные строки (раздел 6).
